계약이 있으면 구현은 에이전트에게 맡길 수 있습니다. 이 장에서 사람이 하는 일은 글을 쓰는 것이 아니라 역할을 지키게 하는 것입니다. 에이전트는 계약을 SKILL.md로 옮기고 빠진 것과 모호한 것을 보고합니다. 사람은 모호한 지점을 결정하고 승인합니다. 산출물은 .agents/skills/paper-reading/SKILL.md입니다.

누가 무엇을 정하는가

이 단계에서 가장 자주 생기는 문제는 에이전트가 계약에 없는 정책을 "합리적으로 보여서" 끼워 넣는 것입니다. 계약은 연구자가 쓴 경계이고, 에이전트는 그 경계를 문서 형식으로 옮기는 역할입니다. 역할을 표로 고정해 둡니다.

역할책임하지 않는 것
연구자계약 작성, 모호한 정책의 최종 결정, SKILL.md 생성 승인, 작업용 계약 파일 삭제SKILL.md를 손으로 처음부터 쓰기
에이전트계약을 SKILL.md로 변환, 계약 내용이 모두 옮겨졌는지 대조, 모호하거나 충돌하는 지점 보고계약에 없는 정책을 결정해 넣기
SKILL.md이후 그 업무가 들어올 때마다 읽히는 유일한 실행 규칙규칙 파일과 템플릿의 내용을 복사해 담기
규칙 파일·템플릿여러 업무가 공유하는 형식과 저장 규칙 제공특정 Skill의 호출 조건이나 중지 조건 담기

Skill이 참조하는 세 문서의 수명

SKILL.md는 어떻게 생겼나

SKILL.md는 frontmatter와 본문으로 됩니다. frontmatter의 name은 Skill 이름이고, description은 에이전트가 "이 요청에 이 Skill을 열까"를 판단할 때 읽는 문장입니다. 계약의 Trigger가 여기로 압축됩니다. 어떤 요청에서 호출하고 어떤 요청에서는 호출하지 않는지가 description 안에 들어가야 트리거가 작동합니다.

# paper-reading

## Overview
(이 문서가 정하는 것과 위임하는 것. 참조 문서 표)

## 호출 조건 / ## 입력 / ## 절차 / ## 도달한 상태별로 남기는 것
## 갱신 범위 / ## 완료 보고 / ## 중지와 질문 / ## 마지막 점검

본문의 절 이름과 개수는 정해진 형식이 없습니다. 에이전트마다, 실행마다 달라집니다. 계약의 여섯 필드가 어디로 갔는지만 추적되면 됩니다. 강의 실습에서는 trigger가 "호출 조건"으로, output이 "도달한 상태별로 남기는 것"과 "갱신 범위"와 "완료 보고" 셋으로 갈라졌습니다. 절이 늘어난 것은 문제가 아닙니다.

생성에서 승인까지의 순서

  1. 생성 전 계획 보기

    어떤 파일을 만들고 지울지 먼저 보여 달라고 합니다. .agents/skills/paper-reading/SKILL.md 하나만 새로 만들어야 합니다. 다른 파일을 만들거나 고치겠다고 하면 멈춥니다.

  2. 변환

    에이전트가 계약과 규칙 파일을 읽고 SKILL.md를 씁니다. 규칙 파일의 절차를 복사하지 않고 "llm_wiki/AGENTS.md의 「서지 확정」 절을 따른다"처럼 가리키게 합니다.

  3. 대조

    계약의 각 조항이 SKILL.md 어디에 반영됐는지 표로 보고하게 합니다. 강의 실습에서는 계약 69개 조항을 기계 대조해 69개 모두 옮겨진 것을 확인했습니다. 숫자 자체보다 "빠진 조항이 없다"는 사실이 중요합니다.

  4. 모호한 지점 보고

    계약을 아무리 잘 써도 이 보고는 항상 나옵니다. 강의에서는 두 가지가 나왔습니다. 개념 페이지(concepts/) 생성 규칙이 계약에도 규칙 파일에도 없다는 것, 그리고 PDF는 받았는데 서지 대조가 실패했을 때 사본을 저장할지 여부가 비어 있다는 것.

  5. 결정

    사람이 정합니다. 강의에서는 개념 페이지 생성 조건을 llm_wiki/AGENTS.md에 추가하고(공용 규칙이므로 Skill이 아니라 규칙 파일에), 미식별 PDF는 sources/_unidentified/에 보관하는 쪽으로 정했습니다. 결정한 내용은 계약에도 반영한 뒤 다시 대조합니다.

  6. 승인과 정리

    대조가 끝나면 작업용 계약 파일을 지웁니다. 같은 규칙이 두 곳에 남으면 실행 규칙의 출처가 둘이 됩니다. 수업에서는 비교용으로 part4/에 사본을 옮겨 두어도 되지만 루트에는 두지 않습니다.

Q 3-1에이전트가 만든 SKILL.md에 "원문이 없으면 초록을 근거로 간단 요약을 작성한다"는 절차가 들어 있습니다. 계약에는 없던 문장입니다. 이것은 좋은 보완일까요, 문제일까요? 어떻게 처리해야 할까요?

답을 적으면 해설이 열립니다.

문제입니다. 두 가지 이유로요. 첫째, 에이전트가 계약에 없는 정책을 스스로 결정했습니다. 역할표에서 "하지 않는 것"에 해당합니다. 둘째, 내용도 Part 3 규칙과 충돌합니다. 원문 미확보는 metadata_only로 멈추고 요약을 추정하지 않는다는 자동 중단 조건이 있습니다.

처리는 그 문장을 삭제하게 하고, 왜 추가했는지 묻습니다. 대개 "계약에 원문 미확보 시 Summary 칸을 어떻게 할지가 명시되지 않았다"는 답이 돌아옵니다. 그러면 그것은 모호한 지점으로 보고했어야 할 것이지 결정해 넣을 것이 아닙니다. 계약의 Output에 "Summary는 비워 둔다"를 추가하고 다시 대조합니다. 에이전트가 모호함을 보고 대신 결정으로 메우기 시작하면 생성 프롬프트에 "계약에 없는 정책은 추가하지 말고 목록으로 보고하라"를 더 강하게 적습니다.

Q 3-2SKILL.md가 완성된 뒤에도 루트에 paper-reading_실행계약.md를 그대로 두면 어떤 일이 생길 수 있을까요? 구체적인 상황 하나를 떠올려 보세요.

답을 적으면 해설이 열립니다.

실행 규칙의 출처가 둘이 됩니다. 예를 들어 04장 테스트에서 재실행 규칙을 고쳐야 해서 SKILL.md를 수정했다고 합시다. 루트의 계약 파일은 옛 규칙 그대로입니다. 몇 주 뒤 에이전트가 루트 파일을 훑다가 계약을 읽고 옛 재실행 규칙을 따르거나, 다음 사람이 계약을 "현재 규칙"으로 믿고 읽을 수 있습니다.

그래서 대조가 끝나면 계약을 지우거나, 최소한 루트 밖(part4/ 같은 작업 폴더)으로 옮기고 "생성 당시의 설계 문서, 현재 규칙은 SKILL.md"라고 적어 둡니다. 계약이 아깝다고 느껴지면 그 내용은 이미 SKILL.md 안에 다 있다는 것을 떠올리면 됩니다. 대조 표가 그 증거입니다.

실습 3

계약을 SKILL.md로 변환하고 승인하기

약 20분

목표

02장에서 쓴 paper-reading_실행계약.md를 에이전트에게 주어 .agents/skills/paper-reading/SKILL.md를 만들고, 대조와 모호한 지점 보고를 받은 뒤 결정하고 승인합니다.

3-1. 생성 요청

part4/paper-reading_생성프롬프트.md의 생성 요청을 바탕으로 한 요청문입니다. 각 줄이 왜 있는지 한 번 읽고 보냅니다. "복제하지 말고 참조", "생성 전 계획", "계약에 없는 정책 금지", "대조 표", "모호한 지점 보고", "승인 전 삭제 금지"가 들어 있습니다.

작업공간 루트의 paper-reading_실행계약.md 와 현재 llm_wiki의 규칙
(llm_wiki/AGENTS.md, llm_wiki/research/AGENTS.md, llm_wiki/papers/_template.md)을 바탕으로
.agents/skills/paper-reading/SKILL.md 를 만들어줘.

조건:
1. 규칙 파일과 템플릿의 내용은 복제하지 말고, 필요한 순서에서 해당 절을 가리켜서 참조해.
2. 생성하기 전에 어떤 파일을 만들고 어떤 파일을 고치거나 지울지 먼저 보여줘.
   새로 만드는 파일은 SKILL.md 하나여야 해.
3. frontmatter의 description에 호출하는 요청과 호출하지 않는 요청을 모두 담아줘.
4. 계약에 없는 정책을 추가하지 마. 계약이 정하지 않은 것이 있으면 결정하지 말고
   "모호한 지점" 목록으로 보고해.
5. SKILL.md를 만든 뒤, 계약의 각 조항이 SKILL.md의 어느 절에 반영됐는지 표로 대조해줘.
   빠진 조항이 있으면 적어줘.
6. 호출 조건, 누락 입력 처리, 저장 위치, 중지 조건, 재실행 규칙 중 모호하거나
   규칙 파일과 충돌하는 부분을 스스로 점검해서 보고해줘.
7. 생성한 SKILL.md를 규칙 파일·템플릿과 비교해 같은 규칙이 두 곳에 적힌 부분을 찾고,
   참조로 줄이는 수정안을 함께 제안해. 내 승인 전에는 고치지 마.
8. 작업용 계약 파일은 내 승인 전에는 지우지 마.

3-2. 생성 결과 검토 (사람)

생성된 SKILL.md를 열어 일곱 가지를 봅니다. part4/paper-reading_생성프롬프트.md의 검토 포인트와 같습니다.

  • 사용 조건: description만 읽어도 어떤 요청에서 쓰이는지 분명하다
  • 입력 게이트: 필수 입력이 없으면 질문하고 멈춘다는 문장이 있다
  • 절차: 템플릿과 규칙 파일을 올바른 순서로 참조한다
  • 출력과 저장: 파일 위치와 완료 보고 항목이 계약과 일치한다
  • 중지 조건: 계약의 Stop / Ask가 빠짐없이 옮겨졌다
  • 책임 중복: 템플릿 본문이나 규칙 파일의 절차 전문이 복사돼 들어오지 않았다
  • 단일 원본: 대조 표에서 빠진 조항이 없다

3-3. 모호한 지점 결정하고 승인하기

에이전트가 보고한 모호한 지점과 중복 문장마다 셋 중 하나로 결정합니다. (가) 이 Skill만의 규칙이면 계약에 추가한다. (나) 여러 업무에 공통인 규칙이면 llm_wiki/AGENTS.md나 research/AGENTS.md에 추가한다. (다) 지금 정할 필요가 없으면 "미결"로 적고 넘어간다. 결정, 반영, 재대조, 승인, 계약 파일 정리를 요청문 하나로 보냅니다.

보고한 모호한 지점과 중복 문장에 대해 다음과 같이 결정했어.
[번호]: [결정 내용]
[번호]: [결정 내용]
중복 문장: 제안한 대로 참조로 줄여.

순서대로 해줘.
1. 결정을 paper-reading_실행계약.md 에 먼저 반영하고, 그다음 SKILL.md에 반영해.
   공용 규칙으로 정한 것은 SKILL.md가 아니라 [해당 규칙 파일]의 [절]에 추가해.
2. 계약과 SKILL.md를 다시 대조해서 빠진 조항이 없는지 확인해.
3. 빠진 조항이 없으면 루트의 paper-reading_실행계약.md 를
   part4/paper-reading_실행계약_생성시점.md 로 옮기고, 파일 맨 위에
   "이 파일은 SKILL.md 생성 당시의 설계 문서다. 현재 실행 규칙은
   .agents/skills/paper-reading/SKILL.md 가 유일한 출처다." 한 줄을 추가해.
   빠진 조항이 있으면 옮기지 말고 멈춰서 알려줘.
4. 끝나면 .agents/skills/ 트리와 루트 파일 목록을 보여줘.

확인할 것

  • .agents/skills/paper-reading/SKILL.md가 있고, 그 외에 새로 생긴 파일이 없다
  • description에 "호출하지 않는 요청"이 들어 있다
  • 대조 표에 빠진 조항이 없다
  • 모호한 지점마다 내가 결정했고, 에이전트가 대신 결정한 것이 없다
  • 루트에 계약 파일이 남아 있지 않다

참고본과 비교하기

part4/참고/paper-reading_SKILL.md를 열어 내 것과 비교합니다. 절 구성이 달라도 됩니다. 볼 것은 Overview의 참조 문서 표(무엇을 규칙 파일에 위임했는지), "도달한 상태별로 남기는 것" 절, 그리고 "중지와 질문" 절에서 여러 편을 함께 처리할 때 한 편의 중지가 나머지를 막지 않게 한 문장입니다. 내 SKILL.md에 필요하다고 판단한 것만 계약을 거쳐 반영합니다.

실패하면

대조 표에 빠진 조항이 있으면 그 조항만 반영하게 하고 다시 대조합니다. 에이전트가 규칙 파일 본문을 그대로 복사했으면 3-3의 중복 점검 결과에서 해당 문장을 참조로 줄이게 합니다. SKILL.md 외의 파일을 만들었다면(예: 별도 체크리스트 파일) 삭제하게 하고, 그 내용이 필요하면 SKILL.md 안에 넣습니다. 세 번 고쳐도 대조가 안 맞으면 계약 쪽 문장이 모호한 것이니 계약을 먼저 고칩니다.
