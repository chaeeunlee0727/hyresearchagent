이 장부터 paper-reading Skill을 한 사이클 만듭니다. 사이클은 설계, 구현, 검증 세 단계이고 이 장은 설계입니다. 설계라고 해서 절차를 처음부터 다시 쓰는 것이 아닙니다. 절차와 출력 형식은 Part 3에 이미 있습니다. 여기서 정하는 것은 그 절차를 언제 시작하고, 무엇이 있어야 시작하고, 어디서 멈추는지의 경계입니다. 산출물은 paper-reading_실행계약.md 한 장입니다.

설계, 구현, 검증: 한 사이클

설계 재료는 Part 3에서 이미 준비되어 있습니다.

  • llm_wiki/papers/_template.md. 논문 페이지 형식과 frontmatter의 상태 필드. Skill의 출력 형식이 됩니다. 새로 쓰지 않습니다.
  • llm_wiki/AGENTS.md. 새 논문 처리 절차, 상태값 정의, 서지 확정과 중복 처리 규칙.
  • llm_wiki/research/AGENTS.md. 프로젝트 문서와 Literature Matrix를 만들 때의 규칙.
  • Part 3에서 처리한 실제 논문 페이지들. 절차가 실제로 돌아간다는 증거이고, 04장 테스트의 비교 기준입니다.

여섯 요소 중 Process와 Output은 이 재료로 사실상 끝나 있습니다. 이 장에서 채울 것은 Trigger, Input, Stop / Ask, Validation입니다.

Trigger: 언제 호출하고 언제 호출하지 않는가

호출 조건은 "하는 경우"만 적으면 반쪽입니다. 비슷하지만 호출하면 안 되는 요청과, 어느 쪽인지 모호한 요청까지 적어야 트리거가 됩니다.

요청호출 여부이유
"이 arXiv 논문 Wiki에 넣어 줘"호출새 논문 추가
"저번에 넣은 그 논문, 검증까지 마저 해 줘"호출기존 페이지의 상태 진행
"이 논문 추가하고 프로젝트 문헌 목록도 갱신해 줘"호출논문 추가에 따른 프로젝트 갱신
"이 논문에서 쓴 loss가 뭐였지?"호출하지 않음내용 질문. 파일을 바꾸지 않는다
"papers 폴더를 연도별 하위 폴더로 나눠 줘"호출하지 않음Wiki 구조 변경
"프로젝트 literature.md의 열 순서 좀 바꿔 줘"호출하지 않음논문 추가 없는 프로젝트 문서 정리. research 규칙을 직접 따른다
"이 논문 좀 봐 줘"모호Wiki 파일이나 상태를 바꾸려는 건지 먼저 묻고 시작한다

모호한 요청을 "일단 추가"로 해석하지 않습니다. 의도가 정해진 뒤에만 다음 단계로 넘어갑니다. 논문 근거를 다시 확인해 달라는 요청은 먼저 답변으로 처리하고, 확인 결과 페이지를 고쳐야 할 때만 Skill을 부릅니다.

눌러 보기: 이 요청에 paper-reading이 열려야 할까

표에 없는 요청 다섯 개입니다. 하나씩 골라 보세요. 고르면 이유가 열립니다.

"어제 넣은 2024_Wang 페이지, 원문 PDF 구했으니 요약까지 진행해 줘"

호출. 기존 페이지의 상태를 metadata_only에서 앞으로 진행시키는 요청이라 Trigger의 "기존 페이지의 보완이나 상태 진행"에 해당합니다.

"topics/ 허브 페이지들을 알파벳순으로 다시 정렬해 줘"

호출하지 않음. 논문 추가가 없는 Wiki 구조·정리 작업입니다. llm_wiki/AGENTS.md를 직접 따릅니다.

"이 arXiv 링크 어때?" (링크만 붙어 있음)

먼저 묻기. 의견을 묻는 것인지 Wiki에 넣으라는 것인지 알 수 없습니다. "Wiki에 추가할까요, 내용만 말씀드릴까요?"라고 확인한 뒤 시작합니다.

"2023_Yeom 페이지 Summary에 적힌 식각률 수치가 원문 표 3이랑 맞는지 봐 줘"

호출하지 않음(일단은). 근거 재확인 요청은 먼저 답변으로 처리합니다. 확인 결과 수치가 틀려서 페이지를 고쳐야 하면 그때 호출합니다.

"papers 폴더에 파일명 규칙 안 맞는 게 몇 개 있는데 고쳐 줘"

호출. 참고본 계약은 파일명 정정을 Trigger에 넣었습니다. 파일명만 바꾸면 허브·index 링크가 깨지므로 Skill이 링크까지 함께 고칩니다. 단, 여러 편이면 변경 목록을 먼저 보여 주고 승인 후 적용합니다.

Input: 무엇이 있어야 시작하는가

필수 입력은 논문을 식별할 수 있는 정보입니다. DOI, arXiv ID, 공식 URL, 또는 제목과 공식 공개 페이지. 사용자가 원문 PDF를 직접 줄 수도 있습니다. 선택 입력은 연결할 연구 프로젝트, 비교하고 싶은 질문, 특별히 볼 부분이고, 없어도 진행합니다.

여기서 두 가지를 분명히 해 둡니다.

  • 받은 값을 그대로 믿지 않습니다. 사용자가 준 DOI나 제목은 외부 서지 DB(Crossref, arXiv, DataCite, 발행처 아카이브)에서 대조해 확정합니다. 대조되지 않으면 페이지를 만들지 않고 묻습니다. 제목만 받았을 때 후보가 여럿이면 어느 논문인지 묻습니다.
  • 원문은 필수 입력이 아닙니다. 원문을 못 구해도 확인된 서지까지는 기록할 수 있습니다. 원문 확보 여부는 입력 조건이 아니라 아래 상태 전이에서 판정합니다.

DB에 논문이 없는 것과 DB에 접근하지 못한 것도 구분합니다. 네트워크가 끊겨 Crossref에 못 갔다면 "이 논문은 DB에 없다"가 아니라 "접근 실패"라고 밝히고 멈춥니다. 둘을 섞으면 멀쩡한 논문이 식별 실패로 기록됩니다.

Output: 입력 상태에 따라 어디까지 가는가

입력 상태에 따라 어디까지 진행하고 어떤 상태로 남길지를 미리 정합니다. 이 표가 있어야 에이전트가 중간에 막혔을 때 추측으로 메우지 않고 정해진 상태로 멈춥니다.

입력 상태동작결과 상태
서지를 외부 DB에서 확인 못 함 (식별 실패)아무 파일도 만들지 않고 어떤 논문인지 묻는다멈춤
기존 페이지와 중복인지 모호새 페이지를 만들지 않고 묻는다멈춤
연도·제1저자 중 한 값만 확인자리표시자 파일명으로 저장needs_review / unreviewed
서지는 확정, 원문 미확보확인된 서지와 실패 사유만 저장metadata_only / unreviewed
원문 확보, 텍스트 추출 불가실패 사유를 남기고 멈춤needs_review / needs_review
원문 확보, 아직 요약 전중간 상태로 기록하고 계속 진행fulltext_available / unreviewed
정상요약(summarized) → 원문 대조까지 진행, 허브·index·log 갱신critically_reviewed / verified 또는 partial·unsupported

출력과 갱신 범위도 계약에 적습니다. 논문 페이지는 _template.md 형식을 따르고, 연도·저장소·학회·토픽 허브와 index를 갱신하고, 프로젝트를 지정했을 때만 그 프로젝트의 literature.md를 갱신하고, log.md에 변경 기록을 남깁니다. 이 목록에 없는 경로는 출력에 넣지 않습니다. 단, _template.md의 내용과 규칙 파일의 절차를 계약에 복사하지는 않습니다. 필요한 시점에 원본을 참조하도록 가리키기만 합니다. 같은 규칙이 두 곳에 있으면 한쪽을 고쳤을 때 다른 쪽이 낡습니다.

Stop / Ask와 Validation

Skill이 안전하게 반복되려면 멈춰야 할 때 확실히 멈춰야 합니다. 위 표에서 "묻는다"로 끝나는 두 경우에 프로젝트 대상이 모호한 경우를 더한 것이 Stop / Ask입니다. 새 프로젝트 생성과 논문 추가를 함께 요청받으면 논문은 공통 Wiki까지만 처리하고, 프로젝트 생성은 research 규칙의 승인 절차를 안내한 뒤 승인 전에는 하지 않습니다.

그 밖의 중지는 묻지 않습니다. 원문을 못 구했다고 매번 사람을 부르면 Skill을 쓰는 의미가 없습니다. 정해진 상태로 저장하고 종료한 뒤 완료 보고에서 "사람 확인 필요"로 표시합니다. 프로젝트를 지정하지 않은 단순 논문 추가는 중지 사유가 아닙니다.

같은 논문이 다시 들어오면 기존 페이지부터 확인해 새 정보가 있는 부분만 갱신하고, 새 정보가 없으면 "변경 없음"으로 끝냅니다. 이것이 재실행 규칙입니다.

Validation은 실행을 끝내기 전에 실제 파일과 대조할 항목입니다.

  • 같은 논문의 페이지, 허브 항목, 상호 링크, log.md 항목이 중복되지 않았는가
  • processing_status / evidence_status가 실제로 도달한 처리 단계와 일치하는가
  • 프로젝트를 지정하지 않았다면 프로젝트 문서가 그대로인가
  • 완료 보고에 적힌 생성·수정 파일이 실제 변경과 일치하는가
실행 계약 여섯 필드

Trigger(호출 조건) · Input(필수·선택 입력) · Process(절차, 재실행 동작) · Output(상태별 결과와 갱신 범위, 완료 보고) · Stop / Ask(멈추고 물을 조건) · Validation(끝내기 전 대조 항목). part4/실행계약_템플릿.md가 이 순서로 되어 있습니다.

Q 2-1"이 논문 추가해 줘"라는 요청과 함께 arXiv ID를 받았습니다. Crossref와 arXiv API 둘 다 타임아웃이 났습니다. 에이전트는 어떻게 해야 할까요? "식별 실패"로 묻는 것과 무엇이 다를까요?

답을 적으면 해설이 열립니다.

"DB에 접근하지 못했다"고 밝히고 멈춥니다. 페이지는 만들지 않습니다. 식별 실패와 다른 점은 보고 내용입니다. 식별 실패는 "이 ID로 논문을 찾을 수 없으니 어떤 논문인지 알려 달라"고 묻는 것이고, 접근 실패는 "지금은 대조할 수 없으니 나중에 다시 시도하거나 다른 DB를 쓰겠다"는 것입니다.

둘을 섞으면 네트워크 문제로 멀쩡한 논문이 "DB에 없음"으로 기록되고, 다음 사람이 그 기록을 믿게 됩니다. 계약의 Input 절에 "DB에 없는 경우와 접근 못 한 경우를 구분한다"고 한 줄 적어 두면 이 혼동을 막을 수 있습니다.

Q 2-2서지는 Crossref에서 확정됐지만 원문 PDF를 어디서도 구하지 못했습니다. 에이전트가 사람에게 물어야 할까요, 아니면 어떤 상태로 저장하고 끝내야 할까요? 저장한다면 Summary 칸은 어떻게 할까요?

답을 적으면 해설이 열립니다.

묻지 않고 metadata_only / unreviewed로 저장하고 종료합니다. 확인된 서지와 "원문을 확보하지 못한 사유"까지만 기록합니다. Summary, 방법, 결과, 수치, 한계는 추정해서 채우지 않고 비워 둡니다. 초록만 보고 요약을 쓰는 것도 안 됩니다.

이 경우는 Stop / Ask가 아닙니다. 사람이 결정할 것이 없고(원문이 없다는 사실은 물어도 달라지지 않습니다), 정해진 상태로 남기면 나중에 원문을 구했을 때 그 페이지에서 이어 갈 수 있습니다. 완료 보고에서 "원문 미확보, 사람 확인 필요"로 표시해 두면 됩니다. 허브 등록은 확인된 저자·연도·venue에만 하고 topic 연결은 원문을 볼 때까지 보류합니다.

실습 2

paper-reading 실행 계약 쓰기

약 25분

목표

part4/실행계약_템플릿.md를 복사해 작업공간 루트에 paper-reading_실행계약.md를 만들고 여섯 필드를 채웁니다. 완벽하게 채우려 하지 않습니다. 03장에서 에이전트가 모호한 지점을 보고하면 그때 메웁니다.

2-1. 범위 카드부터 (5분, 사람)

계약을 쓰기 전에 아래 일곱 줄을 메모장에 먼저 적습니다. 긴 Process부터 쓰기 시작하면 규칙 파일을 그대로 베끼게 됩니다. 경계부터 정하고 절차는 마지막에 씁니다.

항목내 결정
Skill 이름paper-reading
호출하는 요청 (3개)
호출하지 않는 비슷한 요청 (2개)
없으면 시작하지 않을 필수 입력
있으면 좋은 선택 입력
먼저 물어봐야 하는 상황 (3개)
절대 하지 않을 행동 (2개)

2-2. 계약 채우기 (15분, 사람)

템플릿을 복사한 뒤 이 순서로 채웁니다. Trigger → Input → Output(상태 전이표와 갱신 범위) → Stop / Ask → Process → Validation. 다음을 지킵니다.

  • 규칙 파일에 이미 있는 형식은 복사하지 않고 "llm_wiki/AGENTS.md의 서지 확정 절을 따른다"처럼 가리킵니다.
  • 모든 상대 경로는 AGENTS.md가 있는 작업공간 루트 기준이라고 첫머리에 적습니다.
  • Output에는 위 상태 전이표를 자기 말로 옮깁니다. 표를 그대로 붙여도 됩니다.
  • Process에는 재실행 동작("같은 논문이 다시 오면 기존 페이지부터 확인")을 반드시 넣습니다.

2-3. 에이전트에게 계약 검토 맡기기 (5분)

계약을 저장한 뒤 에이전트에게 읽히고 빈틈을 묻습니다. 아직 SKILL.md를 만들지 않습니다.

작업공간 루트의 paper-reading_실행계약.md 를 읽어줘.
그리고 llm_wiki/AGENTS.md, llm_wiki/research/AGENTS.md, llm_wiki/papers/_template.md 도 읽어줘.

다음을 확인해서 알려줘.
1. Trigger에 "호출하지 않는 요청"과 "모호할 때의 동작"이 있는가
2. Input에서 필수 입력이 없을 때의 동작이 적혀 있는가
3. Output의 상태 전이가 llm_wiki/AGENTS.md의 상태 필드 정의와 어긋나는 곳이 있는가
4. Stop / Ask의 각 조건에 "답을 받기 전까지 하지 않는 행동"이 붙어 있는가
5. 규칙 파일이나 템플릿에 이미 있는 문장을 계약이 복사해 온 곳이 있으면 어디인지
6. 계약과 규칙 파일이 서로 반대되는 조항이 있으면 어디인지

계약 파일을 고치지는 마. 번호별로 지적만 해줘.
지적마다 계약의 어느 줄, 규칙 파일의 어느 절인지 적어줘.

확인할 것

  • 논문 식별자가 없을 때 파일을 만들지 않는다는 문장이 있다
  • 프로젝트를 지정하지 않으면 프로젝트 문서를 건드리지 않는다는 문장이 있다
  • 원문 확보 실패와 식별 실패가 다른 상태로 갈라져 있다
  • 같은 논문 재실행 때 새 페이지를 만들지 않는다는 문장이 있다
  • 완료 보고 항목이 실제 파일과 대조 가능한 것들(파일 경로, 상태값)로 적혀 있다

참고본과 비교하기

여기까지 하고 나서 part4/참고/paper-reading_실행계약.md를 엽니다. 강의에서 완성한 계약입니다. 내 계약에 없는 조항을 찾아 "왜 이게 필요했을까"를 생각해 봅니다. 미식별 PDF를 _unidentified/에 보관하는 규칙, 여러 편을 받았을 때 한 편의 중지가 다른 편을 막지 않게 하는 규칙, "간단히 정리해 줘"를 검증 생략으로 해석하지 않는 규칙이 아마 빠져 있을 것입니다. 필요하다고 판단한 것만 내 계약에 옮깁니다. 참고본을 통째로 바꿔치기하면 03장에서 에이전트가 보고하는 모호한 지점이 내 것이 아니게 됩니다.

실패하면

에이전트가 5번(복사해 온 문장)을 여러 곳 지적하면 그 문장을 지우고 참조로 바꿉니다. 6번(반대되는 조항)이 나오면 규칙 파일 쪽이 더 정형화된 절차인지 확인하고, 대개 계약을 규칙 파일에 맞춥니다. 규칙 파일을 고쳐야 한다고 판단되면 계약이 아니라 규칙 파일을 고치되 그 이유를 log.md에 남깁니다.
