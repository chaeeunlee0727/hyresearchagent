설계, 구현, 검증 사이클을 한 바퀴 돌았습니다. 이 장에서는 같은 사이클을 01장에서 고른 내 업무로 한 번 더 돕니다. 새로 배우는 절차는 없습니다. 대신 "입력이 달라지면 계약의 어디가 달라지는가"를 봅니다. 강의가 두 번째로 만든 experiment-log(실험 로그 정리) Skill이 그 사례입니다. 논문에는 DOI라는 깔끔한 식별자가 있었지만 실험 메모에는 형식이 없습니다. 이 차이 하나가 Input, Stop / Ask, Output을 어떻게 바꾸는지 보고, 같은 질문을 내 업무에 던집니다.

뼈대는 같고, 입력이 다르다

두 Skill의 뼈대는 같습니다. 입력을 확인하고, 기존 기록이 있는지 보고, 원본에서 사실을 뽑아 정해진 양식에 저장하고, 막히면 정해진 지점에서 멈추고, 끝내기 전에 실제 파일과 대조합니다. 다른 점은 여섯 가지이고, 전부 입력의 성격에서 나옵니다. 오른쪽 열이 내 업무로 Skill을 짤 때 스스로에게 물을 질문입니다.

사례: Run 17 메모 해부하기

experiment-log가 받는 입력은 이런 메모입니다. 실험을 끝낸 날 급하게 적은 글이라 그날의 나에게는 다 이해되지만 3주 뒤의 나에게는 그렇지 않고, 다른 실험과 비교할 수도 없습니다.

합성 야간 2000장을 넣었다. 야간이 오르고 주간이 유지되는지 보려는 실험. Run 15 대비 야간은 +4.3, 주간은 -0.3. 주간이 낮아진 이유는 아직 모른다. 비율 0.4 때문인지, 재분할 54.7인 이미지의 라벨 어긋남 때문인지. 다음 실험은 1000장으로 줄이거나, 재분할이 낮은 장만 빼고 2000장을 유지하거나. GPU 시간과 일정 때문에 어느 쪽을 먼저 할지는 내가 고를 일이다.

한 문단에 측정된 사실, 추측, 아직 정하지 않은 판단이 섞여 있습니다. Skill이 하는 일은 이것을 풀어서 칸이 나뉜 기록으로 저장하는 것입니다. 풀기 전에 사람이 먼저 분류해 봐야 Skill이 무엇을 하는지 알 수 있습니다.

눌러 보기: 메모의 문장을 칸으로 나누기

Run 17 메모의 문장 일곱 개입니다. 각각 기록의 어느 칸에 들어가야 할지 고르세요.

"합성 야간 2000장을 넣었다"

설정 사실. 단, 원천은 메모가 아니라 config입니다. 메모의 "2000장"과 run17.yaml의 값이 같은지 Skill이 대조하고, 다르면 config 쪽을 적고 불일치를 표시합니다.

"Run 15 대비 야간은 +4.3, 주간은 -0.3"

측정 사실이지만 메모에 적힌 숫자는 "연구자 서술"로 관찰 칸에 넣고, 대비 칸에는 결과표(results.csv)에서 직접 계산한 값만 적습니다. 두 run의 절대값과 평가 조건이 같았다는 확인도 함께 남깁니다.

"비율 0.4 때문인지, 재분할 54.7인 이미지의 라벨 어긋남 때문인지"

가설(원인 후보). 후보마다 확인 방법을 한 줄씩 붙여 적습니다. 비율 0.4 → "합성을 1000장으로 줄여 본다", 라벨 어긋남 → "재분할 낮은 장만 빼고 2000장 유지". 어느 쪽이 맞는지 Skill이 판정하면 범위 밖입니다.

"야간이 오르고 주간이 유지되는지 보려는 실험"

실험 목적. 기록 맨 위의 "목적" 칸에 그대로 들어갑니다. 결과가 아니라 "무엇을 보려 했는가"라서 사실도 가설도 아닙니다. 이 칸이 있어야 나중에 "그래서 봤는가"를 판정할 수 있습니다.

"다음 실험은 1000장으로 줄이거나, 재분할이 낮은 장만 빼고 2000장을 유지하거나"

다음 실험 후보. "승인 대기 후보" 칸에 두 건을 나란히, 우선순위 없이 적습니다. 어느 것을 먼저 할지는 바로 아래 문장에서 연구자가 자기 몫이라고 선언했으므로 Skill은 순서를 매기지 않습니다.

"GPU 시간과 일정 때문에 어느 쪽을 먼저 할지는 내가 고를 일이다"

사람이 정할 일. 기록에는 "다음 후보 두 가지"까지만 적고 우선순위는 비워 둡니다. Skill이 "1000장부터 하자"고 적으면 계약 위반입니다.

"주간이 낮아진 이유는 아직 모른다"

열린 질문. "모른다"는 그 자체로 기록할 가치가 있는 상태입니다. 비워 두지 말고 "원인 미확인"으로 적어야 3주 뒤에 다시 볼 수 있습니다.

입력 네 종류와 신뢰 수준, 그리고 원본 불변

이 Skill의 입력은 네 종류이고 각각 믿을 수 있는 정도가 다릅니다. 메모에 "2000장"이라고 적혀 있어도 진짜 조건은 config에 있습니다.

원천이 갈라져 있으니 충돌이 생깁니다. 결과표의 수치와 메모의 서술이 다를 때 우선순위로 한쪽을 덮어쓰지 않고 멈춰서 묻습니다. 나머지 안전 규칙도 같은 태도입니다.

  1. 원본 불변. 로그, config, 결과 파일은 읽기만 하고 수정하거나 지우지 않습니다. 구조화 결과는 항상 별도 파일에 저장합니다. 원본 메모는 연구 기록의 원천 증거입니다.
  2. 실험 ID 규칙. 같은 ID의 기록이 있으면 새로 만들지 않고 변경분만 갱신합니다. paper-reading의 재실행 규칙과 같은 원칙입니다.
  3. 대비는 근거가 있을 때만. 두 실험의 숫자가 있어도 평가 데이터셋, split, 클래스, 마스크 규칙이 같다고 원본에서 확인될 때만 대비를 계산합니다. 확인되지 않으면 그 지표의 대비 칸을 "확인 필요"로 둡니다.
  4. baseline이 없으면 멈춥니다. baseline이 지정됐는데 구조화된 기록이 없고 같은 요청에 원본도 없으면 "baseline부터 기록할까요?"라고 묻고 중지합니다. 비교만 빼고 진행하지 않습니다. 강의 초기 계약은 "비교만 생략하고 진행"이었다가 이 규칙으로 보완됐습니다. 비교가 빠진 기록은 나중에 비교가 있었던 것처럼 읽히기 때문입니다.
  5. 프로젝트를 정할 수 없으면 묻습니다. 어느 연구 프로젝트의 experiments/에 넣을지 알 수 없을 때입니다.

출력: 관찰, 원인 후보, 확인 방법을 열로 나눈다

저장 위치는 프로젝트의 experiments/<run_id>.md, 형식은 세팅 2에서 추가한 research/_template/experiment.md입니다. 양식의 윗부분은 항목·값·근거 위치 세 열의 표입니다. 모든 값에 어느 파일 어느 줄에서 왔는지가 붙습니다. Part 3에서 논문 판단마다 원문 위치를 요구한 것과 같은 원칙입니다.

관찰된 값은 같은 실행의 사실로 한 상자에 들어가고, 메모에 적힌 "+4.3"은 검증 전 서술이므로 연구자 서술로 따로 둡니다. 결과표로 직접 계산한 대비만 대비 칸에 들어갑니다. 설명이 필요한 관찰에는 원인 후보를 여러 개 붙이되 확인 방법은 후보마다 하나씩 적습니다. 조건을 한 번에 하나만 바꿔야 결과를 보고 원인을 짚을 수 있기 때문입니다.

다음 실험 후보는 형식이 중요합니다. 확인 목적, 변경 변수와 유지 조건, 기대 관찰과 성공 기준, 리스크와 필요한 승인이 다 채워져야 합니다. 다음 Part의 실험 플래너가 후보들을 비교하려면 형식이 같아야 합니다. 원본에서 확인하지 못한 칸은 추정해 채우지 않고 "확인 필요"로 남깁니다. 원본에 후보가 없으면 없음과 그 근거 위치를 적습니다.

강의에서 확인한 결과

계약 54개 항목을 SKILL.md와 대조해 누락 없이 옮겨졌습니다. 충돌이 1건 나왔습니다. 계약의 Process 2번 항목과 research 규칙 파일의 실험 기록 절차가 서로 반대되는 조항이었고, 규칙 파일 쪽이 더 정형화된 절차라고 판단해 SKILL.md를 규칙 파일에 맞춰 고쳤습니다.

실행 요청은 "run15, run17을 정리해 줘"였습니다. 프로젝트를 지정하지 않았는데, 에이전트는 config에 적힌 프로젝트명을 읽어 그 프로젝트를 찾아 진행했습니다. 의존 순서대로 run15(baseline)를 먼저 구조화한 뒤 run17을 처리했고, 대비를 계산한 지표는 dark-junction validation mIoU 하나뿐이었습니다. 나머지는 config의 evaluation 블록에 야간 데이터셋만 적혀 있어 평가 조건이 같다고 말할 수 없으므로 "확인 필요"로 남겼습니다. 실제로 config에는 dark-junction만 있는데 결과 CSV에는 Cityscapes 값도 들어 있어 원본 간 불일치가 있는 상태였습니다. run15는 기준선이라 다음 실험 후보를 만들지 않았고, run17에는 메모의 후보 두 건이 우선순위 없이 승인 대기로 남았습니다.

프로젝트를 묻지 않고 config에서 읽어 진행한 부분은 06장에서 다시 봅니다.

① 입력을 무엇으로 특정하나? 외부에서 확인 가능한가?
② 원본이 여럿이면 어느 값은 어디서? 충돌하면?
③ 결과는 어디에? 공통 자산인가 프로젝트 소유인가?
④ 같은 입력이 다시 오면 중복인가 보강인가?
⑤ Skill이 읽는 파일 중 사람이 직접 쓰는 것은? (원본 불변)
⑥ 중간에 끼어드는 연구자 판단은? 어떻게 비워 두나?
복사해서 계약 파일 맨 위에 붙여 두면 A-2에서 고칠 곳이 바로 보입니다.

A-2. 계약 고치기 (8분, 사람)

part4/paper-reading_실행계약_생성시점.md를 루트에 [skill-name]_실행계약.md로 복사합니다. 처음부터 쓰지 않습니다. 카드의 답이 가리키는 필드만 고칩니다. ①②는 Input과 Stop / Ask, ③은 Output과 Stop / Ask, ④는 Process의 재실행 줄, ⑤는 Output의 "쓰지 않는 곳", ⑥은 Trigger의 범위 밖과 Output의 비워 두는 칸입니다. 고치지 않은 필드가 많아도 괜찮습니다. 그것이 "뼈대는 같다"의 뜻입니다. 끝나면 02장 2-3의 검토 요청문을 Skill 이름만 바꿔 보내 빈틈을 받습니다.

A-3. SKILL.md 생성과 승인 (7분)

03장 3-1의 생성 요청문에서 계약 파일명과 Skill 이름만 바꿉니다. 참조할 규칙 파일도 바뀔 수 있습니다. 결과가 프로젝트 안으로 가는 Skill이면 llm_wiki/research/AGENTS.md와 그 템플릿을, 공통 Wiki로 가는 Skill이면 llm_wiki/AGENTS.md를 적습니다.

작업공간 루트의 [skill-name]_실행계약.md 와 [참조할 규칙 파일·템플릿]을 바탕으로
.agents/skills/[skill-name]/SKILL.md 를 만들어줘.

조건:
1. 규칙 파일과 템플릿의 내용은 복제하지 말고 필요한 순서에서 해당 절을 참조해.
2. 생성 전에 만들 파일과 고칠 파일을 먼저 보여줘. 새 파일은 SKILL.md 하나여야 해.
3. description에 호출하는 요청과 호출하지 않는 요청을 모두 담아줘.
4. 계약에 없는 정책을 추가하지 말고, 계약이 정하지 않은 것은 "모호한 지점"으로 보고해.
5. 만든 뒤 계약의 각 조항이 SKILL.md 어느 절에 반영됐는지 대조표를 보여주고,
   계약과 규칙 파일이 서로 반대되는 조항이 있으면 알려줘.
6. 내 승인 전에는 계약 파일을 지우지 마.

모호한 지점은 03장 3-3과 같은 요청문으로 결정·반영·승인하고, 계약은 part4/[skill-name]_실행계약_생성시점.md로 옮깁니다.

A-4. 두 번 실행하기 (7분)

04장의 세 시나리오 중 둘만 합니다. 요청문은 내 업무에 맞게 직접 씁니다.

  1. 중지 확인: 카드 ①이나 ③에서 "없으면 멈춘다"고 한 입력을 일부러 빼고 보냅니다. 묻고 멈추는지, 파일이 하나도 안 생기는지 봅니다.
  2. 정상 실행: 필수 입력을 다 넣어 보냅니다. 실행 전 계획과 실행 후 보고(생성·수정 파일, 확인하지 못한 값, 사람이 볼 항목)를 요구하는 것은 04장 요청문과 같습니다. 끝나면 보고와 실제 변경(git status --short 또는 스냅샷)을 대조하고, 카드 ⑤의 원본 파일이 바뀌지 않았는지 따로 확인합니다.

재실행 시나리오는 06장 체크리스트에서 두 Skill을 같이 볼 때 돌립니다.

확인할 것

  • 카드의 여섯 질문에 모두 답이 있고, 그 답이 계약의 어느 필드로 갔는지 말할 수 있다
  • 계약에서 고친 필드가 paper-reading과 다른 이유를 한 줄씩 설명할 수 있다
  • 중지 확인 실행에서 파일 변경이 0개였다
  • 정상 실행에서 보고 = 실제 변경이고, 원본 파일은 그대로다
  • 연구자 판단 자리(카드 ⑥)가 기록에서 비어 있거나 "후보"로만 적혀 있다
B. 막막하다면: experiment-log를 이어서 실습하기 (강의의 두 번째 Skill, 가상 원본 제공)

강의가 만든 experiment-log를 그대로 따라 만듭니다. 위 A와 같은 사이클이고, 계약을 고칠 곳은 이 장 첫 표의 experiment-log 열이 알려 줍니다. 실행은 두 번 합니다. 프로젝트를 빼고 보내 중지를 확인한 뒤, 프로젝트를 지정해 보냅니다.
