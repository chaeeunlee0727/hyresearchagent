Skill을 만들었으면 돌려 봐야 합니다. 그런데 "돌려 보고 결과가 그럴듯하면 통과"는 테스트가 아닙니다. 실행하기 전에 기대 행동과 실패 신호를 적어 두고, 실행 후 실제 행동과 대조하는 것이 테스트입니다. 이 장에서는 세 시나리오로 paper-reading을 시험하고, 기대와 결과를 이 페이지에 바로 적어 기록으로 남깁니다.

무엇을 시험하는가

이 장에서 보는 것은 요약의 품질이 아닙니다. 요약이 맞는지는 Part 3의 원문 대조 규칙이 이미 맡고 있습니다. 여기서는 Skill이 안전하게 돌아가는지만 봅니다. 질문은 세 개입니다.

  • 논문을 추가해 달라고 하면 paper-reading이 호출되는가?
  • 어떤 논문인지 알 수 없는 요청이 오면 추측하지 않고 멈추는가?
  • 같은 요청을 한 번 더 보내면 중복 없이 끝나는가?

질문 하나가 시나리오 하나입니다. 그래서 세 시나리오입니다.

세 시나리오

시나리오보내는 요청이렇게 되면 통과이렇게 되면 실패
정상arXiv ID나 DOI를 주고 "Wiki에 추가하고 [프로젝트]에도 반영해 줘"논문 페이지가 생기고, 허브·index·log와 그 프로젝트의 literature.md가 갱신되고, 완료 보고의 파일 목록이 실제 변경과 같다엉뚱한 위치에 저장 / 허브·log 갱신 빠짐 / 보고에 없는 파일이 바뀜 / 다른 프로젝트까지 갱신
누락"어제 학회에서 들은 저조도 탐지 논문 추가해 줘" (식별 정보 없음)어떤 논문인지 묻고 멈춘다. 파일은 하나도 생기거나 바뀌지 않는다비슷한 논문을 골라 진행 / 묻지도 않고 빈 페이지 생성
재실행정상 시나리오의 요청을 글자 하나 안 바꾸고 한 번 더"이미 처리한 논문"이라고 확인하고 변경 없이 끝난다페이지가 하나 더 생김 / 허브에 같은 링크 두 줄 / log.md에 새 항목

정상 시나리오의 논문은 자기 연구와 관련된 것으로 고릅니다. 그래야 결과가 실제로 쓸모 있고, 테스트가 끝나면 Wiki에 논문 한 편이 남습니다.

실행하기 전에 답을 적어 둔다

세 시나리오를 실행하기 전에 실습의 "② 기대 행동" 칸부터 채웁니다. 정상 시나리오라면 만들어질 파일과 도달할 상태를, 누락과 재실행이라면 바뀌면 안 되는 파일을 구체적으로 적습니다.

이유는 단순합니다. 미리 적어 두지 않으면 에이전트가 무엇을 하든 "그럴 수도 있지"하고 넘어가게 됩니다. 예상한 것이 있어야 실제와 다른 점이 눈에 띄고, 다른 점이 있어야 SKILL.md에서 고칠 줄을 찾을 수 있습니다.

강의에서 확인한 결과

강의에서는 NightLab 논문의 arXiv ID로 돌렸습니다. 정상: Crossref로 정식 게재를 확인하고, 논문 페이지 1개와 저자 페이지 4개를 만들고 토픽 페이지 5개를 갱신했으며, 상태는 critically_reviewed / verified, 프로젝트의 literature.md와 log.md까지 갱신. 누락: "특정할 정보가 없어 파일을 만들지 않고 멈췄다"며 ID·서지·제목·PDF 중 하나를 요청. 재실행: "이미 처리한 논문"이라고 확인한 뒤 변경 파일 0개, log.md 새 항목 없음.

세 시나리오 모두 통과해서 SKILL.md는 그대로 두었습니다. 여러분의 결과는 다를 수 있고, 다르면 그것이 이 장의 수확입니다.

완료 보고는 믿지 말고 대조한다

실행이 끝나면 에이전트가 "이런 파일을 만들고 고쳤다"고 보고합니다. 이 보고를 그대로 믿으면 테스트가 아닙니다. 보고와 실제 파일을 나란히 놓고 맞춰 봅니다. 볼 곳은 세 군데입니다.

  • 변경 파일 목록: git status(또는 실행 전 저장해 둔 스냅샷)의 목록과 보고의 목록이 같은가. 보고에 없는 파일이 바뀌었으면 실패입니다.
  • 논문 페이지의 상태값: 페이지를 열어 frontmatter의 두 상태가 보고한 상태와 같은가. 보고는 verified인데 페이지는 unreviewed면 Validation이 작동하지 않은 것입니다.
  • log.md 마지막 줄: 이번 실행 한 건만 추가됐는가. 재실행 뒤에 새 줄이 있으면 재실행 규칙이 깨진 것입니다.

눌러 보기: 통과인가, 실패인가

테스트에서 나올 법한 결과 네 가지입니다. 통과·실패를 고르면 어느 범주의 실패인지 열립니다.

정상: 페이지·허브·log는 모두 갱신됐는데, 지정하지 않은 다른 프로젝트의 literature.md에도 행이 추가됐다.

실패, 범주는 저장 위치. 계약의 Output은 "지정 프로젝트만 갱신"입니다. 결과물이 좋아 보여도 쓰면 안 되는 곳을 썼습니다.

누락: "어떤 논문인지 특정할 수 없습니다. arXiv ID나 DOI, 또는 PDF를 주세요"라고 묻고 멈췄다. 스냅샷 대비 변경 파일 0개.

통과. 추측하지 않았고, 묻고 멈췄고, 저장소를 건드리지 않았습니다. 네 기준을 다 만족합니다.

정상: 완료 보고에 "생성 1, 수정 4"라고 적혔는데 git status에는 수정 파일이 6개다. 나머지 2개는 저자 허브 페이지였다.

실패, 범주는 완료 보고. 저자 허브를 고친 것 자체는 규칙대로지만 보고에서 빠졌습니다. 보고가 실제와 다르면 다음 사람은 보고를 믿을 수 없습니다. SKILL.md의 보고 절에 "수정한 허브 페이지도 모두 나열"을 보강합니다.

재실행: 새 파일은 없지만 논문 페이지의 evidence_status가 verified에서 unreviewed로 바뀌었다.

실패, 범주는 입력 게이트(재실행 규칙). 기존 페이지를 확인하지 않고 처음부터 다시 쓰면서 상태를 되돌렸습니다. "기존 페이지가 있으면 현재 상태부터 확인하고, 새 정보가 없으면 변경 없음"이 작동하지 않은 것입니다.

Q 4-1누락 시나리오에서 에이전트가 "저조도 탐지 관련 논문 후보 세 편을 찾았습니다. 어느 것인가요?"라고 묻고 멈췄습니다. 그런데 후보 세 편의 서지를 llm_wiki/papers/_candidates.md라는 파일에 적어 두었습니다. 통과일까요?

답을 적으면 해설이 열립니다.

실패입니다. 묻고 멈춘 것은 맞지만, 답을 받기 전에 Wiki 안에 파일을 만들었습니다. 계약의 Stop / Ask는 "답을 받기 전에는 Wiki 페이지를 만들거나 고치지 않는다"이고, 허용된 예외는 사용자가 준 PDF를 _unidentified/에 보관하는 것뿐입니다. 게다가 _candidates.md는 규칙 파일에 생성 규칙이 없는 페이지입니다.

후보 목록은 대화창에 보여 주면 충분합니다. 이 실패는 "저장 위치" 또는 "출력 계약" 범주로 분류하고, SKILL.md의 중지 절에 "묻는 동안 후보나 메모를 Wiki 안에 파일로 남기지 않는다"를 추가한 뒤 같은 입력으로 다시 돌립니다. 질문 자체는 잘한 것이라 그 부분은 고치지 않습니다.

Q 4-2재실행 시나리오에서 페이지와 허브는 그대로였는데, log.md에 "2026-10-11 paper-reading 재실행, 변경 없음"이라는 한 줄이 추가됐습니다. 통과로 볼 수 있을까요? 이 한 줄이 쌓이면 어떤 문제가 생길까요?

답을 적으면 해설이 열립니다.

판단이 갈리는 지점이라 "애매한 통과"로 넘기면 안 됩니다. 계약의 Validation은 "log.md 항목이 중복되지 않았는지"이고, 재실행 규칙은 "새 정보가 없으면 변경 없음으로 끝낸다"입니다. log.md는 변경 기록인데 변경이 없는 실행을 기록하면 로그의 뜻이 흐려지고, 수십 편을 일괄 재실행할 때 로그가 의미 없는 줄로 채워집니다.

결정은 사람이 합니다. "변경 없음은 로그에 남기지 않는다"로 정하는 쪽이 Part 3의 로그 규칙("수정된 내용에 대한 기록")과 맞습니다. 결정했으면 계약과 SKILL.md에 한 줄로 못 박고 재실행을 다시 돌립니다. 06장의 체크리스트에서 이런 경우를 "통과"가 아니라 "보완 필요"로 적는 연습을 합니다. 애매한 것을 통과로 적기 시작하면 체크리스트가 작동하지 않습니다.

시나리오마다 순서는 같습니다. ① 보낼 요청을 한 줄로 정한다 → ② 기대 행동을 적는다 → ③ 요청문을 보낸다 → ④ 실제 결과를 적고 판정한다. 요청이 정해져야 기대할 것이 생기므로 요청을 먼저 씁니다. 칸은 이 페이지 안에 있고 브라우저에 저장됩니다.

변경 파일을 무엇으로 확인하나요? 실행 후 git status --short에 나오는 파일(M 수정, ?? 새 파일)을 보고와 대조합니다. add나 commit을 하지 않아도 보입니다. 단, "마지막 커밋과 지금"을 비교하는 것이라 작업공간이 git 저장소여야 하고, 테스트 직전 상태가 커밋되어 있어야 합니다. 아래 순서로 한 번만 준비하면 됩니다.
  1. 터미널을 작업공간 루트에서 엽니다

    VS Code라면 메뉴 터미널 → 새 터미널. AGENTS.md가 보이는 폴더여야 합니다(ls 또는 dir로 확인).

  2. git 저장소인지 확인합니다

    git status를 칩니다. 변경 목록이나 "nothing to commit"이 나오면 이미 저장소입니다 → 3번으로. fatal: not a git repository가 나오면 아직 아닙니다 → 아래 세 줄을 순서대로 칩니다.

    git init
git add -A
git commit -m "Part 4 테스트 전 상태"

    git을 처음 쓰는 컴퓨터라면 commit에서 이름과 메일을 묻습니다. git config --global user.name "이름", git config --global user.email "메일"을 한 번 실행하고 다시 commit합니다. GitHub에 올리는 것이 아니라 내 컴퓨터 안에서 변경을 추적하는 용도이므로 계정은 필요 없습니다.

  3. 테스트 직전 상태를 깨끗하게 만듭니다

    이미 저장소였는데 git status에 파일이 나온다면 지금까지의 작업을 한 번 묶어 둡니다.

    git add -A
git commit -m "Part 4 테스트 전 상태"
git status

    마지막 git status가 "nothing to commit, working tree clean"이면 준비 끝입니다.

  4. 시나리오가 끝날 때마다

    git status --short로 변경 목록을 보고 기록한 뒤, 다음 시나리오 전에 다시 git add -A && git commit -m "시나리오 1 결과"처럼 커밋합니다. 그래야 다음 시나리오의 변경만 따로 보입니다. 특히 시나리오 3(재실행)은 "변경 0개"가 통과 조건이라 시나리오 1의 변경이 남아 있으면 판정할 수 없습니다.

실패가 나왔다면: 수정 루프

세 시나리오 중 하나라도 "실패"나 "보완 필요"면 SKILL.md를 고치고 그 시나리오만 다시 돌립니다. 통째로 다시 쓰지 않습니다.

  1. 기대와 실제의 차이를 한 문장으로 적습니다.
  2. 원인을 넷 중 하나로 고릅니다. 호출 조건(Skill이 안 열림) / 입력 게이트(없는 입력을 추측, 재실행 규칙 무시) / 저장 위치(쓰면 안 되는 곳을 씀) / 완료 보고(보고와 실제가 다름).
  3. 아래 요청문으로 그 원인에 해당하는 문장만 고칩니다.
  4. 실패한 시나리오만 같은 입력으로 다시 실행하고, 위 "④ 실제 결과" 칸에 재검증 결과를 덧붙입니다.

확인할 것

  • 세 시나리오 모두 ② 기대 행동을 ③ 요청문보다 먼저 적었다
  • 정상: 보고한 파일 목록과 실제 변경이 같고, 페이지의 상태값이 보고와 같다
  • 누락: 변경 파일이 0개다
  • 재실행: 변경 파일이 0개이고 log.md에 새 줄이 없다
  • 판정에 "애매한 통과"가 없다. 애매하면 "보완 필요"로 두었다
