Skill을 두 개 만들고 각각 실행까지 마쳤습니다. 마지막은 두 Skill을 같은 기준으로 점검하는 체크리스트입니다. 체크리스트의 목적은 "다 통과했다"는 표를 만드는 것이 아니라, 05장에서 남겨 둔 애매한 사례처럼 넘어가기 쉬운 것을 잡아 Skill을 한 번 더 고치는 것입니다. 산출물은 두 Skill 분량의 part4/skill_품질_체크리스트.md와 수정 1회입니다.

내용의 검증과 실행의 검증

범위를 먼저 긋습니다. Part 2~3에서 한 것은 내용의 검증입니다. 사실과 추론을 구분하고, 근거 위치를 찾게 하고, 원문과 대조시키고, 확인 못 한 항목은 그렇다고 표시하는 것. 이 규칙은 AGENTS.md와 llm_wiki/AGENTS.md에 있고 Skill이 참조합니다.

이 장의 범위는 실행의 검증입니다. 필요할 때 호출되는가, 위험할 때 멈추는가, 같은 입력을 안전하게 다시 처리하는가. Skill을 도구로 믿고 반복해서 쓸 수 있는지를 묻는 질문이고, SKILL.md와 테스트 기록으로 판정합니다. 요약의 품질이 낮다면 그것은 체크리스트가 아니라 규칙 파일의 문제입니다.

평가 기록 방법

기준마다 다섯 칸을 남깁니다. 결과(통과 / 보완 필요 / 해당 없음), 근거(테스트 기록, 생성 파일, 변경 내역, 완료 보고 중 어디), 문제(기대 행동과 실제 행동의 차이), 수정(SKILL.md에서 바꾼 최소 항목), 재검증(다시 실행한 시나리오와 결과). 실행 기록 없이 인상만으로 통과 판정하지 않습니다. "잘 되는 것 같다"는 근거가 아닙니다. 근거 칸에는 파일 경로나 기록표의 행 번호가 들어가야 합니다.

강의에서 확인한 결과

두 Skill 모두 Trigger, Procedure, Output contract, Idempotency, Scope, Testability는 통과했습니다. paper-reading은 Input gate와 Stop / Ask도 통과했습니다. experiment-log는 프로젝트를 지정하지 않은 요청에서 config에 적힌 프로젝트명을 읽어 진행했기 때문에 Input gate와 Stop / Ask가 "약간 애매한 상태"였고, 강의에서는 일단 통과로 보고 넘어갔습니다.

이 자료에서는 그 사례를 통과로 적지 않습니다. 계약의 Stop / Ask에는 "저장할 연구 프로젝트를 정할 수 없을 때 묻는다"가 있고, 실제 행동은 묻지 않고 진행한 것입니다. 결과가 나쁘지 않았다고 해서 계약과 행동의 차이가 사라지지는 않습니다. 애매한 것을 통과로 적기 시작하면 체크리스트는 다음 Skill부터 작동하지 않습니다.

처리 방법은 둘 중 하나이고 어느 쪽이든 괜찮습니다. 결정하지 않고 두는 것만 안 됩니다.

선택결정고칠 곳
(가) 지정으로 인정"config의 project 필드로 확인되면 프로젝트가 지정된 것으로 본다." baseline을 config 필드로 인정하는 규칙과 같은 방식계약의 Input 절에 한 줄 추가 → SKILL.md 반영. 행동은 그대로, 규칙이 행동을 따라감
(나) 사용자 명시만 인정"프로젝트는 요청문에서 사용자가 지정한 것만 인정한다. config의 값은 확인용으로만 쓰고, 요청에 없으면 묻는다"SKILL.md의 입력·중지 절 수정 → 5-3 재실행. 규칙은 그대로, 행동이 규칙을 따라감

어느 쪽을 고를지는 연구 환경에 달렸습니다. config에 프로젝트명을 항상 적는 팀이라면 (가)가 편하고, 같은 config를 여러 프로젝트에서 돌려 쓰는 팀이라면 (나)가 안전합니다.

수정 루프

판정에서 "보완 필요"가 나오면 네 단계를 돕니다. 04장의 실패 처리와 같은 절차입니다.

  1. 차이 확인

    기대했던 행동과 실제 파일·보고를 비교해 차이를 한 문장으로 적습니다.

  2. 원인 특정

    왜 실패했는지를 기준과 조건으로 특정합니다. "Stop / Ask의 프로젝트 조건이 '정할 수 없을 때'로만 되어 있어 config 값이 있으면 정할 수 있다고 해석됨"처럼.

  3. 최소 수정과 재실행

    SKILL.md(필요하면 계약 사본도)에서 그 문장만 고치고 같은 시나리오를 다시 실행합니다.

  4. 기록

    결과가 좋으면 체크리스트의 수정·재검증 칸에 적습니다. 문제가 남으면 1번으로 돌아갑니다.

Q 6-1paper-reading이 논문 추가 요청에서는 매번 호출됩니다. 그런데 "이 논문에서 쓴 backbone이 뭐였지?"라는 질문에도 열려서 페이지를 다시 읽고 상태를 갱신하려 들었습니다. Trigger 기준은 통과일까요? 어디를 고쳐야 할까요?

답을 적으면 해설이 열립니다.

보완 필요입니다. Trigger는 양쪽을 봅니다. 필요할 때 호출되는 것만으로는 반쪽이고, 무관한 요청에서 조용해야 통과입니다. 내용 질문에 끼어든 것은 실패입니다.

고칠 곳은 SKILL.md frontmatter의 description입니다. 에이전트가 Skill을 열지 말지 판단할 때 읽는 문장이 거기이기 때문입니다. "논문 내용에 관한 단순 질문에는 호출하지 않는다"가 빠져 있거나 약하게 적혀 있을 것입니다. 본문의 호출 조건 절에만 적혀 있으면 소용이 없습니다. Skill이 열린 뒤에야 읽히는 곳이니까요. 고친 뒤에는 같은 질문을 다시 보내 Skill이 열리지 않는지, 그리고 논문 추가 요청에는 여전히 열리는지 양쪽을 다시 확인합니다.

Q 6-2체크리스트의 Testability 행에 결과 "통과", 근거 "테스트 했음"이라고 적혀 있습니다. 이 기록의 문제는 무엇이고, 근거 칸에는 무엇이 들어가야 할까요?

답을 적으면 해설이 열립니다.

근거가 확인 가능한 것을 가리키지 않습니다. "테스트 했음"은 인상입니다. 3주 뒤의 내가, 또는 다른 연구자가 이 행을 보고 어디를 열어 확인해야 하는지 알 수 없습니다.

근거 칸에는 part4/paper-reading_테스트기록.md의 세 행(정상·누락·재실행)이 모두 채워져 있다는 사실과 그 파일 경로, 그리고 05장 실행 보고의 검수 포인트 여덟 개 중 몇 개를 확인했는지가 들어가야 합니다. Testability가 묻는 것은 "테스트를 했는가"가 아니라 "다음에 또 테스트할 수 있는 기록이 남아 있는가"입니다. 기록표가 없으면 이 기준은 통과가 아니라 보완 필요입니다.
