이 교재에서 다루는 것#

세 번째 파트에서는 논문이 들어올 때마다 같은 품질로 처리되는 파이프라인을 완성했습니다. 한 문장 요청이면 수집, 요약, 검증, 매트릭스 갱신까지 돌아가는 것이죠.

네 번째 파트에서는 여기서 한 단계 더 나아갑니다. 지금까지 잘 돌아가던 절차를 재사용 가능한 부품, 즉 스킬로 만듭니다. 필요할 때마다 불러와서 실행하는 방식이고요.

이 파트가 끝나면 논문 읽기와 실험 로그 정리라는 두 개의 스킬이 연구 공간에 생기고, 앞으로 어떤 업무든 같은 방식으로 원하는 스킬을 만들 수 있는 제작 패턴과 품질 체크리스트도 함께 남게 됩니다.

세 장의 읽는 순서#

  • 01장 — 판단: 스킬이 반복 절차를 담는 문서라는 정의는 이미 배웠습니다. 이 장에서는 "잘 돌아가는데 왜 굳이 스킬을 만드는가"와 "어떤 업무부터 스킬로 옮겨야 하는가" 두 질문에 답하고, 그 결과를 판단 기준표라는 파일로 남깁니다.
  • 02장 — 설계·구현·검증: 페이퍼 리딩 스킬을 한 사이클로 만듭니다. 실행 계약을 설계하고, Claude가 그 계약을 skill.md로 구현하며, 세 가지 시나리오(정상·누락·재실행)로 검증합니다.
  • 03장 — 재사용: 같은 패턴을 실험 로그 정리에 재사용하고, 마지막에는 두 스킬을 같은 기준으로 점검하는 품질 체크리스트를 만듭니다.

설명을 위한 비유와 가상 사례는 실제 강의 실습과 구분해 표시합니다. 처음부터 파일 이름이나 명령을 외울 필요는 없습니다.

규칙이 문서 여러 곳에 나눠져 있으면 생기는 문제#

세 번째 파트에서 마지막에 했던 것을 떠올려 보면, "이 논문을 위키에 추가하고 프로젝트까지 갱신해줘"라는 한 문장 요청으로 수집·요약·검증·매트릭스 갱신까지 돌아가는 파이프라인을 완성했습니다.

짧은 요청으로 이것이 가능했던 이유는 규칙이 문서에 나눠서 적혀 있었기 때문입니다. claude.md에서 검증 규칙을 읽고, LLMWiki 폴더의 README에서 처리 절차와 상태 규칙을 따라가고, research 폴더의 README에서 프로젝트 갱신 규칙까지 적용해 논문 페이지·허브 페이지·index.md·log.md를 갱신했죠.

그런데 여기에 문제가 있습니다. 규칙이 프로젝트 전체가 공유하는 루트 문서와 폴더별 README에 나눠져 있어서, 논문 추가라는 특정 업무의 절차 전체가 파일 여러 개에 흩어져 들어가 있는 것입니다. 여기에 원고 검토 절차, 분야별 데이터 정리 절차까지 더해지면 모든 대화가 시작될 때마다 모든 절차를 읽게 됩니다. 실험 로그를 정리하는 중에도 논문 추가 절차가 에이전트의 컨텍스트에 실려 있고, 문서는 점점 길어져 지금 업무와 무관한 규칙이 컨텍스트 대부분을 차지하게 됩니다.

문서의 세 층: 프롬프트 · claude.md · 스킬#

지금까지 쓰는 문서는 세 층으로 나눠 볼 수 있습니다.

층 적용 범위 예
프롬프트이번 요청 한 번에만 적용"17번째 실험 결과 정리해줘", "이 논문 추가해줘" — 목적과 제약을 담아 그 순간에만 읽힘
claude.md프로젝트 전체의 공통 규칙사실과 추론을 구분한다, 출처를 남긴다, 어떤 폴더는 수정하지 않는다, 템플릿 폴더를 복사해서 쓴다 — 어떤 업무든 지켜야 하므로 모든 대화의 시작에 읽힘
스킬조건에 맞는 업무가 들어올 때만 읽힘논문 읽기 요청이 오면 논문 읽기 스킬이 열리고, 실험 로그 요청이 오면 그 스킬이 열림

이렇게 나누면 문제가 풀립니다. 모든 업무의 공통 규칙은 claude.md에 남기고, 업무마다 달라지는 절차는 각자의 스킬로 옮겨 필요할 때만 에이전트의 컨텍스트에 불러옵니다. 다른 업무를 할 때는 컨텍스트를 차지하지 않습니다.

스킬 문서의 6가지 요소와 실행 계약#

스킬 문서 안에는 절차만 들어가는 것이 아닙니다. 절차는 여섯 요소 중 하나일 뿐입니다.

  1. 트리거(사용 조건) — 이 스킬을 언제 시작할지
  2. 인풋 — 시작에 필요한 필수 입력
  3. 프로세스(절차) — 작업 순서
  4. 아웃풋 — 결과를 남길 위치와 형식
  5. 스톱 앤 애스크 — 어떤 상황에서 멈추고 사람에게 물을지
  6. 밸리데이션 — 결과가 맞는지 확인하는 방법

하나씩 빼 보면 왜 다 필요한지 알 수 있습니다. 사용 조건이 없으면 관계없는 요청에도 열리고, 정작 필요할 때 빠질 수도 있습니다. 필수 입력이 없으면 재료가 부족한 채로 시작해 없는 정보를 지어냅니다. 중지가 없으면 확신이 없어도 끝까지 진행해버려 뒷정리에 더 시간이 걸리고, 검증이 없으면 결과가 맞는지 아무도 알 수 없습니다.

다음 챕터에서 실행 계약을 쓸 때 이 여섯 개를 그대로 필드 이름으로 씁니다. 절차만 있는 문서가 아니라 시작 조건·중지 기준·검증 방법까지 묶은 '실행 계약'으로 남기는 이유입니다.

반복된다고 전부 스킬이 되는 것은 아니다#

주의할 점 하나가 있습니다. 반복되는 일이라고 전부 스킬이 되는 건 아닙니다.

  • 스킬로 만들기 좋은 일: 논문 페이지 생성, 실험 로그 구조화 — 입력과 출력이 안정돼 있고, 결과를 기대 행동과 대조해서 시험할 수 있습니다.
  • 연구자의 판단으로 남겨둘 일: 연구 질문 확정, 연구 공백 판단, 다음 실험 선택, 원고 최종 승인 — 연구자가 매주 매일 반복하지만, 연구 질문을 정할 때는 지도 교수의 조언·학회 일정·내 관심사가 함께 적용됩니다. 같은 입력을 반복해서 넣기도 어렵고 결과를 대조할 기준도 일정하지 않습니다.

그래서 횟수만 보고 스킬을 고르지 않습니다. 순서와 결과를 미리 정할 수 있는지, 진행 중에 연구자의 판단이 매번 필요한지를 함께 봐야 합니다. Part 1에서 자동화할 업무와 직접 할 업무를 나눴을 때의 기준을 스킬 고르기에 적용하는 겁니다.

판단 기준표: 5가지 기준으로 순위를 정한다#

매번 감으로 판단하지 않도록 기준표를 만듭니다. 5개의 기준입니다.

기준 보는 것 방향
반복성같은 형태의 요청이 계속 들어오는지높을수록 적합
입력 안정성시작에 필요한 입력의 종류와 형식이 매번 비슷한지높을수록 적합
출력 안정성결과가 들어갈 파일·위치·형식이 정해져 있는지높을수록 적합
검증 가능성기대 행동과 대조해 시험할 수 있는지높을수록 적합
사람 판단 필요도절차 중간에 연구자의 판단이 매번 필요한지낮을수록 적합

Part 1에서 만든 업무 목록에 이 기준을 적용해 평가하면 이렇게 됩니다.

업무 반복성 입력 안정성 출력 안정성 검증 가능성 사람 판단 필요도 판정
논문 원문을 위키 페이지로 구조화(상태·링크·인덱스 갱신)상상상상하1순위
비정형 실험 로그의 구조화(관찰과 원인 후보 분리 저장)상중상상하2순위
문헌 리뷰와 관련성 심사상중중중중다음 파트(에이전트 역할)로 이관
다음 실험 선택·연구 질문 확정----높음연구자 몫으로 유지

업무 명은 "논문 읽기"처럼 넓게 쓰지 않고 "어디까지가 자동화 대상인지"가 드러나게 좁혀서 적어야 평가가 쉽습니다. 동점이 나오면 입력 안정성과 검증 가능성을 먼저 봅니다.

1순위 선정 이유(페이퍼 리딩): ① 내용과 형식이 이미 정해져 있다(Part 3의 논문 템플릿과 두 README가 출력 계약을 거의 완성해 둔 상태), ② 절차가 실제 문헌에서 검증됐다(한 편 처리와 수십 편 일괄 이관을 파이프라인으로 돌려 잘 동작하는 걸 확인), ③ 시험 방법이 분명하다(기대 행동이 문서에 있으니 결과를 대조하면 된다), ④ 남은 일은 포장뿐이다 — claude.md와 README에 흩어져 있던 지시문서를 한 곳에 모아 스킬 틀로 옮기기만 하면 됩니다.

2순위(실험 로그 정리)의 범위 확정: 비정형 로그를 구조화하고 다음 판단에 쓸 후보까지만 만듭니다. 후보 비교·우선순위 제안은 다음 파트의 실험 플래너 에이전트가, 승인은 연구자가, 승인된 프로세스의 반복 운영은 여섯 번째 파트의 루프가 담당합니다.

연구자분들께서 하실 작업: Part 1의 업무 목록 표를 확장해 다섯 기준으로 점수를 매기고, 어떤 스킬을 1순위로 만들지 결정해 보세요. 강의의 예시 두 개와 같을 필요는 없습니다.

다음 챕터에서는 논문 읽기 스킬의 입력과 출력 설계, 즉 실행 계약 작성부터 다룹니다.

02. 페이퍼 리딩 스킬: 실행 계약부터 검증까지

이 페이지에서 다루는 내용

  1. 스킬 제작의 한 사이클: 설계 → 구현 → 검증
  2. 실행 계약에 정하는 것: 호출 조건과 입력
  3. 입력 상태별 상태 전이와 출력 범위
  4. 중지·재실행 규칙과 검증 항목
  5. 계약을 skill.md로 구현하고 승인한다
  6. 세 가지 시나리오로 검증한다

스킬 제작의 한 사이클: 설계 → 구현 → 검증#

이 장의 세 클립은 한 사이클로 이어집니다. 첫 번째 클립에서 실행 계약을 설계하고, 두 번째 클립에서 Claude가 그 계약을 실제 skill.md로 구현하고, 마지막 클립에서 세 가지 시나리오로 스킬을 검증합니다.

스킬이 처리할 작업은 지금까지 손으로 해 온 "논문 한 편을 LLM 위키에 넣는 것"입니다. 요청을 받았을 때 어떤 파일을 읽고 어디까지 갱신할지를 미리 정해 두는 것이 이번 장의 핵심입니다.

설계 재료는 이미 Part 3에서 준비되어 있습니다.

  • papers 폴더의 _template.md — 논문 페이지 형식(프론트메터의 상태 필드 포함). 스킬의 출력 형식이 됩니다. 새로 쓸 필요가 없습니다.
  • LLMWiki 폴더의 README — 새 논문 처리 절차, 상태값 정의, 서지 확정과 중복 처리 규칙이 있습니다.
  • research 폴더의 README — 프로젝트 문서와 문헌 매트릭스를 만들 때의 규칙이 적혀 있습니다.
  • 실제 논문 페이지들 — Part 3에서 처리한 결과가 절차가 실제로 돌아간다는 증거이고, 테스트 때 비교 기준이 됩니다.

즉 6가지 스킬 요소 중 절차와 출력은 사실상 완성된 상태입니다. 이 장에서 정할 것은 네 번째 노드, 사용 조건·필수 입력·중지 같은 실행의 경계입니다.

실행 계약에 정하는 것: 호출 조건과 입력#

먼저 스킬을 호출하는 조건부터 정합니다.

  • 호출하는 경우: "새 논문을 추가해 달라", "기존 페이지를 보완해 달라", "논문 추가에 따라 프로젝트를 갱신해 달라"는 요청이 들어올 때
  • 호출하지 않는 경우: 논문 내용에 답하는 요청, 위키 구조를 바꾸라는 요청
  • 모호한 요청은: 파일이나 상태를 바꾸려는 것인지 먼저 연구자에게 질문해서 확인합니다. 대화의 의도가 정해진 뒤에만 다음 단계로 넘어갑니다.

다음은 필수 입력입니다. 논문을 식별할 수 있는 서지 정보(DOI, arXiv 아이디, 공식 URL)이거나 사용자가 직접 주는 원문 파일이 필요합니다. 선택 입력으로는 연결할 기존 연구 프로젝트, 비교하고 싶은 질문, 주의 깊게 볼 부분이 있습니다.

중지·재실행 규칙과 검증 항목#

스킬이 안전하게 반복되려면 멈춰야 할 때 확실히 멈추는 규칙이 필요합니다.

  • 식별 실패: 아무 파일도 만들지 않고 어떤 논문인지 다시 묻는다
  • 원문 미확보: 서지 페이지와 실패 사유만 남기고 metadata-only 상태로 멈춘다
  • 추출·대조 불가: 실패 사유를 남기고 needs-review로 멈춘다
  • 중복·프로젝트 대상이 모호: 새 페이지나 새 프로젝트를 만들지 않고 연구자에게 묻는다
  • 같은 논문이 다시 들어오면: 기존 페이지부터 확인해서 필요한 부분만 갱신한다

마지막으로 validation 필드에는 실행을 끝내기 전에 실제 파일과 대조할 항목을 적습니다. 페이지·허브 링크·log.md 항목이 중복되지 않았는지, 상태 값이 실제 도달한 처리 단계와 맞는지, 프로젝트를 지정하지 않았다면 프로젝트 문서가 그대로인지, 완료 보고가 실제 생성·수정된 파일과 맞는지까지입니다.

실행 계약 6필드: trigger(호출 조건) · input(필수·선택 입력) · process(절차) · output(상태별 결과와 갱신 범위) · stop-and-ask(멈추고 물을 경우) · validation(실행 후 대조 항목)

  1. 실행 계약 문서 — 스킬 생성 때만 참조하고, 생성 뒤에는 지웁니다.
  2. skill.md — 스킬을 직접 쓸 때 읽는 유일한 규칙 출처. 호출 조건·절차 순서·중지 조건이 적혀 있습니다.
  3. 템플릿과 README — 페이지를 만들 때 참조합니다. README는 스킬이 아니라 일반 프롬프트에서도 계속 읽히는 여러 업무가 공유하는 문서입니다.

강의 실습에서는 69개의 계약 규칙 문장을 기계 대조해 "69×69 이관 완료, 누락 없음"을 확인했습니다. 프론트메터의 overview, trigger→호출 조건, input→입력, process→절차, output 3개, 중지·질문, validation이 그대로 옮겨졌습니다.

skill.md의 필드명과 필드 개수는 정해진 형식이 없어 매번 달라집니다. 계약의 작업이 전부 수행되기만 하면 되므로 필드 개수에 놀라지 않아도 됩니다.

생성 뒤에는 Claude가 모호한 지점을 보고합니다. 계약을 최선으로 써도 이 보고는 항상 나옵니다. 실습에서는 ① concepts 폴더 처리 규칙이 없다는 점, ② PDF는 있는데 서지 대조가 실패할 때 사본 저장 여부가 비어 있다는 점을 지적받고, Claude의 추천대로 "1번은 concepts 생성 규칙을 README에 추가, 2번은 사본을 저장하는 쪽"으로 결정해 스킬을 완성했습니다.

대조가 끝났다면 실행 계약 파일은 직접 삭제합니다. 같은 내용이 두 곳에 남으면 실행 규칙의 출처가 두 개가 되기 때문입니다.

만든 스킬을 시험할 시나리오 세 개와, 스킬이 고장 났을 때 나타날 실패 신호를 먼저 예측해 둡니다.

시나리오 입력 통과 조건 실패 신호

정상 시나리오는 통과했습니다. arXiv 아이디를 받아 Crossref API로 2022년 정식 게재를 확인·대조했고, 논문 페이지가 생성되어 저자 페이지 4개 생성, 토픽 페이지 5개 업데이트, 허브·인덱스 갱신, 도달 상태 critically-reviewed / evidence-verified가 기록됐고, 프로젝트의 literature.md 매트릭스와 저자 페이지, log.md까지 갱신됐습니다.

누락 시나리오도 통과했습니다. "논문을 특정할 정보가 없어서 파일을 만들지 않고 멈췄습니다"라며 arXiv 아이디·서지 정보·정확한 제목·PDF 중 하나를 달라고 요청했고, "LLMWiki 아래 문서들과 프로젝트 문서는 이번 요청으로 아무것도 바꾸지 않았습니다"라고 보고했습니다.

재실행 시나리오도 통과했습니다. "동일한 논문을 이 세션에서 이미 처리했습니다. 중복 생성 없이 현재 상태부터 확인하겠습니다"라고 나왔고, 새로 만들거나 고친 파일이 없었으며 log.md에도 새 항목이 추가되지 않았습니다.

같은 패턴, 새로운 입력: 실험 로그 정리#

이전 챕터에서 설계 → 구현 → 테스트라는 스킬 제작 사이클을 한 바퀴 돌았습니다. 이번에는 그 패턴을 두 번째 업무인 실험 로그 정리에 재사용합니다. 페이퍼 리딩 스킬에서 검증한 실행 계약 틀을 그대로 복사해서 두 번째 업무에 맞게 수정합니다.

다만 이번 스킬이 받는 입력은 논문처럼 깔끔한 식별자가 아닙니다. 사람이 실험을 진행하고 결과를 급하게 적은, 형식이 없는 메모입니다. 예를 들어 Run 17 메모는 이렇게 되어 있습니다.

합성 야간 2000장을 넣었다. 야간이 오르고 주간이 유지되는지 보려는 실험. Run 15 대비 야간은 +4.3, 주간은 -0.3. 주간이 낮아진 이유는 아직 모른다 — 비율 0.4 때문인지, 재분할 54.7인 이미지의 라벨 어긋남 때문인지. 다음 실험은 1000장으로 줄이거나, 재분할이 낮은 장만 빼고 2000장을 유지하거나. GPU 시간과 일정 때문에 어느 쪽을 먼저 할지는 내가 고를 일이다.

한 문단에 측정된 사실(Run 15 대비 야간 +4.3, 주간 -0.3)과 추측(라벨 어긋남 때문)과 미정의 판단(다음 실험 후보)이 섞여 있습니다. 그날의 나에게는 이해되지만 3주 뒤의 나에게는 그렇지 않고, 실험 데이터가 쌓여도 비교할 수 없습니다.

이 스킬은 섞여 있는 메모를 풀어서 형식을 갖춘 실험 기록으로 저장하는 일을 합니다. 단, 실패 원인 확정·다음 실험의 우선순위 결정·실험 실행과 승인은 계약 밖에 둡니다. 우선순위 제안은 다음 파트의 실험 플래너 에이전트가, 승인은 연구자의 몫입니다.

입력 4종과 신뢰 수준, 그리고 원본 불변#

이번 스킬의 입력은 4종이고, 각각 신뢰할 수 있는 수준이 다릅니다.

입력 내용 신뢰 수준
raw log목적과 관찰이 담긴 1차 기록. 사실과 해석이 섞여 있음출발점이자 원천 증거
config 파일어떤 조건으로 실패했는지 파라미터가장 신뢰할 수 있는 원천 (메모에 2000장이라 적혀도 진짜 조건은 여기 있다)
결과표 (CSV)실험 아이디별 수치의 원천수치의 기준
베이스라인 지정비교 대상 실험 기록기록이 없으면 원본을 찾아 먼저 구조화하고, 원본도 없으면 확인 필요로 비워둠

안전규칙 5개 중 가장 중요한 것부터:

  1. 원본 불변 — raw log·config·결과 파일은 읽기만 하고, 구조화 결과는 항상 별도 파일로 저장한다. 원본 메모는 연구 기록의 원천 증거이기 때문에 덮어쓰면 안 됩니다.
  2. 실험 아이디 규칙 — 같은 아이디의 기존 기록이 있으면 변경분만 갱신한다 (페이퍼 리딩의 재실행 규칙과 같은 원칙).
  3. 대비는 근거가 있을 때만 — 두 실험의 숫자가 있어도 평가 조건이 원본에 적혀 있지 않으면 대비 칸은 확인 필요로 둔다. 같은 조건에서 잰 숫자인지 모르는데 비교하면 잘못된 비교입니다.
  4. 결과표와 로그 서술이 다르면 임의로 고르지 않고 연구자에게 묻는다.
  5. 어느 연구 프로젝트에 넣을지 정할 수 없을 때도 연구자에게 묻는다.

출력: 관찰·원인 후보·확인 방법을 열로 나눈다#

구조화된 실험 기록에는 다음 값을 선언해 둡니다.

  • 실험 아이디와 목적 — 무엇을 확인하려던 실험인가
  • 변경 변수 — 베이스라인에서 무엇을 바꿨는가 (Run 17은 합성 야간 2000장)
  • 유지 조건과 평가셋 — 바꾸지 않은 설정, 데이터셋, 클래스 수 등
  • 주요 지표와 대비 변화 — 베이스라인 대비 얼마나 바뀌었는가
  • 근거 위치 — 모든 값이 어느 파일 어느 줄에서 왔는지 (Part 3의 논문 판단마다 원문 위치를 요구했던 것과 같은 원칙)
  • 확인 필요 — 원본에서 답을 찾지 못한 항목은 그렇게 표시해 연구자가 직접 확인한다

저장 위치는 연구 프로젝트의 experiment 폴더 아래, 형식은 research 폴더의 experiment.md 템플릿을 따릅니다.

메모에 섞여 있던 내용은 이렇게 나뉩니다. 관찰된 값(야간 22.9, 주간 76.1, 합성 재분할 54.7)은 한 상자에 같은 실행의 사실로 들어가고, "야간 +4.3 상승, 주간 -0.3 하락"은 검증 전 서술이므로 따로 분리합니다. 설명이 필요한 부분은 원인 후보 둘(비율 0.4 / 라벨 어긋남)을 각각 떼어서 확인 방법을 붙입니다 — 비율 후보는 합성을 1000장으로 줄여보고, 라벨 후보는 재분할이 낮은 장만 빼고 2000장을 유지합니다.

조건은 한 번에 하나만 바꿔야 결과를 보고 원인을 짚어낼 수 있습니다. 스킬은 후보를 구조화해서 승인 대기로 저장하는 데까지만 하고, 후보 비교·우선순위 제안은 실험 플래너 에이전트, 승인은 연구자가 합니다.

다음 실험 후보는 형식이 중요합니다. 확인 목적(어떤 가설을 보려는 실험인지), 변경 변수와 유지 조건, 기대 관찰과 성공 기준, 리스크와 필요한 승인(GPU 시간·일정·성능 하락 가능성·누가 승인하는지) 4항목이 다 채워져야 합니다. 다음 파트의 실험 플래너 에이전트가 후보를 비교하려면 형식이 같아야 하기 때문입니다.

구현과 실행: Run 15·17 정리 실습#

실행 계약 문서(트리거·입력·프로세스·출력·중지와 질문·validation·원본 불변 필드)를 Claude에게 주어 skill.md를 생성합니다.

  • 계약 문서의 54개 항목을 skill.md와 문자열 대조했고, 누락 없이 옮겨졌습니다.
  • 확인 필요한 충돌 1건: 계약의 프로세스 2번째 항목과 research 폴더 README의 실험 기록 절차가 서로 반대되는 조항이었습니다. README가 더 정형화된 프로세스라고 판단해 "skill.md 쪽을 README에 맞춰 고쳐라"로 결정했습니다.

폴더를 열면 페이퍼 리딩 스킬 위에 실험 로그 스킬이 같이 생성되어 있고, Claude Code에서 /실험로그처럼 슬래시 명령으로 트리거 단어 없이도 명시적으로 실행할 수 있습니다.

실행 프롬프트는 "run15, run17을 정리해줘"였습니다. 연구 프로젝트를 지정하지 않았는데, config 파일에 적혀 있던 연구 프로젝트명을 읽어서 그 프로젝트를 찾아 진행했습니다.

실행 결과:

  • 의존 순서대로 run15(베이스라인)를 먼저 구조화한 뒤 run17을 처리했습니다. 원본이 같은 요청에 다 있어서 중지 사유는 없었습니다.
  • 대비를 계산한 지표는 하나뿐입니다. dark-junction validation mIoU만 계산했고, 나머지는 config의 evaluation 블록에 야간 데이터셋만 적혀 있어 평가 조건이 같다고 말할 수 없기 때문에 확인 필요로 남았습니다. (실제로도 config에는 dark-junction만 적혀 있는데 결과 CSV에는 Cityscapes 값도 들어 있어, 원본 간 불일치가 존재하는 상태였습니다.)
  • "야간 +4.3"은 근거가 있는 주장이므로 메모 원문 서술의 근거와 함께 그대로 기록에 남았습니다. 반면 config에서 근거를 확인할 수 없었던 수치는 확인 필요로 남았고, 평가 지표가 아닌 값은 대비하지 않았다고 기록했습니다.
  • run15는 비교 기준선이므로 다음 실험 후보를 만들지 않았고, run17에는 메모 원본에 있던 후보 두 건을 우선순위를 매기지 않고 리스트 형태로 승인 대기 상태로 남겼습니다.

프로젝트의 index.md에는 실험 기록 항목이 추가됐고, 각 기록 파일에는 항목·값·근거 위치가 정리됐으며, 관찰과 실패 원인 후보, 다음 실험 후보가 각각 기록됐습니다.

실행의 검증: 스킬 품질 체크리스트 8기준#

스킬을 두 개 만들고 각각 실행까지 마쳤습니다. 이제 체크리스트를 만들어 두 스킬을 같은 기준으로 평가합니다.

먼저 범위를 정합니다. 지금까지 Part 2~3에서 한 것은 내용의 검증입니다. 사실과 추론을 구분하고, 근거 위치를 찾게 하고, 원문과 대조시키고, 확인 못한 항목은 확인 못했다고 표시 — 이 절차는 claude.md와 readme.md에 기록해 뒀습니다.

오늘의 범위는 실행의 검증입니다. "필요할 때 호출되는가, 위험할 때 멈추는가, 같은 입력을 안전하게 다시 처리하는가" — 스킬을 도구로 믿고 반복해서 쓸 수 있는지를 묻는 질문들이고, skill.md와 테스트 기록으로 판정합니다.

# 기준 묻는 것 판정 근거
1트리거필요한 요청에서 호출되고, 무관한 요청에서는 조용한가호출 테스트 양쪽 (호출이 안 되는 것도 실패, 아무데나 끼어드는 것도 실패)
2입력 게이트필수 입력을 확인하고, 부족하면 만들지 않고 질문하는가식별자 없는 요청 테스트
3프로시저지정된 README·템플릿을 참조해 절차가 이어지는가실행 관측
4출력 계약정해진 파일·위치를 지키고, 완료 보고가 실제 변경과 일치하는가생성 파일과 보고의 대조
5스톱 앤 애스크추측하기 전에 멈추는가, 범위 밖 행동 전에 묻는가누락 시나리오 테스트
6재실행 안정성같은 입력에서 중복 파일·링크·로그를 만들지 않는가재실행 테스트
7스코프사람·서브 에이전트·루프의 몫을 침범하지 않는가 (원인을 확정하지 않았는가, 후보가 변수 하나만 바뀐 채로, 우선순위 없이 승인 대기인가)실행 기록
8테스트 가능성기록표와 검수 포인트가 남아 있는가테스트 기록

두 스킬의 판정 결과: 트리거·프로시저·출력 형식·재실행 안정성·스코프·테스트 가능성은 둘 다 통과. 페이퍼 리딩 스킬은 입력 게이트와 스톱 앤 애스크도 통과. 실험 로그 스킬은 프로젝트 미지정 요청에서 config를 읽어 프로젝트를 찾아 진행해버려서 약간 애매한 상태지만 일단 통과로 보고 넘어갔습니다.

판정에서 수정에 해당하는 항목이 발견되면: ① 기대했던 행동과 실제 파일을 비교해 차이를 확인하고, ② 왜 실패했는지 기준·조건을 특정하고, ③ skill.md를 고쳐 시나리오를 재실행하고, ④ 결과가 잘 나오면 기록하고, 문제가 남으면 이 과정을 반복합니다.
